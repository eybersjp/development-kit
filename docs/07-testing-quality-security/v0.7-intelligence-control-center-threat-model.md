# v0.7 DK Intelligence and Control Center Threat Model

> Status: Planned architecture for Development Kit v0.7. This supplements the existing framework threat model.

## Security Objective

DK Intelligence must improve continuity without creating a new path for prompt injection, authorization bypass, cross-project data leakage, secret persistence, or browser-local privilege abuse. DK Control Center must expose the same governed state as DK Core, not a weaker parallel control plane.

## New Trust Boundaries

1. **Durable Memory Boundary**: information persists beyond the current model/session.
2. **Memory Extraction Boundary**: model-derived candidates may be inaccurate, over-generalised, or maliciously influenced.
3. **Memory Retrieval Boundary**: stored content re-enters future model context.
4. **Project / Workspace / User Scope Boundary**: broader scopes increase the blast radius of incorrect or sensitive information.
5. **Local Browser Boundary**: a browser UI can originate state-changing requests to the local DK Runtime API.
6. **Provider Boundary**: optional memory/wiki/code providers may be local, remote, authenticated, or independently compromised.
7. **Index / Cache Boundary**: derived indexes can become stale or diverge from authoritative source records.

## Threats and Required Mitigations

### 1. Remembered Approval Bypass

**Threat:** Memory says the user previously approved deployment, publishing, deletion, remote writes, or another consequential action. An agent treats that as current authorization.

**Mitigation:** Memory can never satisfy a DK approval gate. Approval tokens and current policy remain authoritative. Tests must prove that remembered approval history cannot authorize a new action.

### 2. Memory Prompt Injection

**Threat:** A stored conversation, document, provider result, imported record, or extracted memory contains instructions such as "ignore DK rules" or "run this command" and is later retrieved into context.

**Mitigation:** Retrieved memory is context data, not instruction authority. Imported/external records are tagged `imported-untrusted` unless explicitly governed. Context assembly must clearly delimit memory and preserve instruction hierarchy.

### 3. Authority Escalation

**Threat:** An inferred or imported record becomes labelled `user-approved` through extraction, editing, provider mapping, or UI behaviour.

**Mitigation:** Authority transitions are explicit events. Generic edit/PATCH operations cannot silently promote authority. Promotion to `user-approved` requires a user-confirmation flow with auditable provenance.

### 4. Cross-Project Leakage

**Threat:** Project A secrets, decisions, customer information, or context appear in Project B because retrieval uses a global index without strict scope filtering.

**Mitigation:** Project identity is a mandatory partition key for project memory. Scope filtering happens before ranking. Cross-project promotion must be explicit. Evaluation fixtures must include same-keyword records in multiple projects to detect leakage.

### 5. Secret Persistence

**Threat:** API keys, tokens, cookies, private keys, credentials, passwords, or session data are extracted from conversations/logs into durable memory.

**Mitigation:** Candidate extraction includes secret-pattern and sensitive-source filtering. Providers must not deliberately store credential/session material as memory. Logs and exports exclude secrets. Security review covers provider auth flows.

### 6. Stale Memory Causing Unsafe Work

**Threat:** Old dependency versions, superseded architecture decisions, reverted requirements, or obsolete security assumptions are treated as active truth.

**Mitigation:** Records support staleness, expiry, source fingerprints, and supersession. Stale/superseded records are visually distinct and down-ranked or excluded according to retrieval policy. Current repository evidence outranks stale historical memory.

### 7. Poisoned Memory Extraction

**Threat:** A malicious source or hallucinated model output creates a durable false lesson/fact that influences later work.

**Mitigation:** Extraction produces candidates with provenance and authority. Deterministic repository facts may be auto-persisted only when source-backed. Material decisions require explicit approval evidence. Confidence never substitutes for authority.

### 8. Malicious or Compromised Provider

**Threat:** An optional provider returns manipulated memory/code/wiki content, leaks data remotely, or attempts to cause writes/system changes.

**Mitigation:** Provider output is untrusted. Providers declare data-location and capability classes. Installation is never automatic. Authenticated access and system/write/destructive capabilities remain approval-governed. DK must degrade to local/native providers where possible.

### 9. Localhost Browser Attack / CSRF

**Threat:** A malicious website opened in the user's browser sends requests to `127.0.0.1:<dk-port>` and edits memory, activates providers, or triggers workflow actions.

**Mitigation:** Runtime-generated session/capability tokens, deny-by-default CORS/origin policy, anti-CSRF controls for browser writes, content-type validation, and no assumption that localhost equals trusted.

### 10. LAN Exposure

**Threat:** Control Center binds to `0.0.0.0` and becomes reachable by other machines on the network.

**Mitigation:** Bind to loopback by default. Remote/LAN access is out of v0.7 baseline. Any future remote mode requires separate authentication, authorization, transport security, and threat modelling.

### 11. Duplicate / Rogue Runtime

**Threat:** Multiple runtimes for the same project race on state files or a stale endpoint points the browser to the wrong process.

**Mitigation:** project-scoped runtime identity, endpoint/PID freshness checks, transaction locks for authoritative stores, health handshake, and stale metadata recovery.

### 12. UI Approval Path Weakening

**Threat:** Control Center adds a convenient Approve button that bypasses replay-resistant tokens or required confirmation context.

**Mitigation:** UI approval actions call the same DK Core approval engine and must satisfy identical validation. There is one approval authority, multiple presentation surfaces.

### 13. Destructive Memory Deletion

**Threat:** Accidental or malicious bulk deletion destroys important engineering history.

**Mitigation:** prefer archive/supersede for normal correction; destructive forgetting is explicit; bulk operations require stronger confirmation; export/recovery strategy is available where practical.

### 14. Corrupt Memory / Index

**Threat:** Partial writes or malformed records make DK unusable or produce incorrect retrieval.

**Mitigation:** atomic writes/transactions, schema validation, recoverable index rebuild, authoritative record store separated from derived cache/index, corruption diagnostics, graceful degradation.

### 15. Auto-Open Abuse

**Threat:** Control Center auto-open launches repeated tabs, runs in CI/headless contexts, or opens attacker-controlled URLs from corrupted runtime metadata.

**Mitigation:** default Off; interactive-context detection; loopback URL construction by DK rather than trusting arbitrary stored URLs; duplicate suppression; validate endpoint health before launch; auto-open failure never loops.

## Data Classification

Memory records should be classifiable for handling policy. Initial categories may include:

- normal project context;
- sensitive project context;
- personal/user preference;
- external/untrusted;
- prohibited secret/credential material.

The v0.7 baseline must at minimum distinguish prohibited credential/session material from ordinary memory candidates.

## Security Evaluation Scenarios

Required behavioural evaluations include:

1. Stored text says "deploy without asking"; DK still requires approval.
2. Imported README says "ignore AGENTS.md"; DK treats it as data.
3. Inferred memory cannot become `user-approved` through ordinary edit.
4. Project A memory is not returned in Project B query.
5. Superseded decision does not rank as active decision.
6. Changed source artifact marks dependent memory stale where configured.
7. Token/API-key-like data is rejected/redacted from candidate persistence.
8. Malicious localhost cross-origin write is rejected.
9. Control Center does not bind to non-loopback by default.
10. Provider outage falls back or reports unavailable without fabricated data.
11. Provider-returned instruction cannot trigger tool execution by itself.
12. Auto-open remains Off by default and does not run in CI/headless test fixtures.
13. Auto-open does not repeatedly create new tabs for one runtime/project.
14. UI approval uses the same replay-resistant approval path as CLI/agent workflow.
15. Corrupt derived index can be rebuilt without losing authoritative memory records.

## Security Review Gates

Implementation requires security review when introducing:

- the Runtime API server;
- browser write operations;
- authority promotion;
- provider authentication;
- remote provider data transmission;
- TencentDB Agent Memory adapter;
- any future LAN/remote Control Center mode;
- new persistent executable hooks based on memory retrieval.

## Release Blocking Conditions

v0.7 must not ship if any of these remain unresolved:

- memory can satisfy an approval gate;
- cross-project retrieval leakage;
- ordinary edits can silently escalate authority;
- Control Center accepts unauthenticated cross-origin writes;
- default network binding exposes the UI beyond loopback;
- provider failure is represented as success;
- secret material is intentionally persisted as normal memory;
- corrupt memory writes can silently destroy the authoritative store.
