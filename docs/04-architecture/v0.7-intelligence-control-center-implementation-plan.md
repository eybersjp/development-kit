# Development Kit v0.7 DK Intelligence and Control Center Implementation Plan

> Status: Planned. This is the implementation sequence after architecture approval. It deliberately separates foundational governance from UI polish and optional provider integrations.

## Objective

Deliver DK Intelligence and DK Control Center as integrated Development Kit capabilities while preserving Development Kit's lightweight installation, provider neutrality, cross-platform support, verification-first workflow, and approval model.

## Delivery Principles

- build the smallest correct local baseline before semantic/vector sophistication;
- retain Node 18 compatibility unless separately changed by an explicit architecture decision;
- do not require Docker or an external service for baseline functionality;
- keep Autopilot state independent from memory;
- implement governance metadata before automated extraction;
- implement Runtime API security before browser write features;
- add optional providers only after the local contract is proven;
- every phase must have independently verifiable acceptance criteria;
- consequential operations remain fail-closed.

## Phase 0: Baseline and Repository Preparation

1. Complete the separate installer dead-code cleanup already identified.
2. Confirm `npm run release:validate` passes on the clean baseline.
3. Record baseline package/runtime compatibility.
4. Freeze v0.7 architecture documents and acceptance criteria.

**Gate:** no known baseline regression is carried into v0.7 implementation.

## Phase 1: Schemas and Project Identity Integration

Implement:

- memory record schema;
- memory candidate schema;
- authority/status/scope enums;
- project/workspace/user scoping rules;
- source/provenance schema;
- supersession model;
- effective settings schema including Control Center auto-open.

Reuse existing project identity where possible rather than creating a competing identity system.

**Tests:** schema validation, invalid authority transitions, project partition keys, settings precedence.

## Phase 2: DK Local Memory Provider

Implement the default local provider with:

- atomic record persistence;
- manifest/index rebuild;
- read/get/query;
- update;
- archive;
- forget;
- supersede;
- export/import groundwork;
- corruption handling.

Initial retrieval can be deterministic filtering + lexical ranking. Embeddings are not required to pass this phase.

**Gate:** complete offline operation with no external provider.

## Phase 3: Staleness and Provenance

Integrate memory records with source evidence and existing staleness concepts:

- artifact references/fingerprints;
- supersession;
- expiry;
- stale status;
- active truth selection;
- provenance display model.

**Tests:** changed source -> stale dependent record; superseded decision excluded from active-decision query; stale records remain inspectable.

## Phase 4: Context Assembly and Retrieval Policy

Implement lifecycle-aware retrieval for DK commands/agents.

Required controls:

- scope filter before ranking;
- authority-aware ranking;
- freshness/staleness handling;
- lifecycle/task relevance;
- context budget;
- explicit memory delimiters in model context;
- source references where useful.

**Gate:** memory improves continuity without flooding the context window.

## Phase 5: Candidate Extraction

Add post-operation candidate generation for selected workflows, beginning with high-signal events such as:

- `/dk-design` decisions/constraints;
- `/dk-debug` verified root-cause lessons;
- `/dk-review` findings;
- `/dk-ship` release lessons.

Candidate pipeline:

```text
work result
  -> candidate extraction
  -> secret/sensitivity filter
  -> authority assignment
  -> deterministic auto-store OR governed candidate queue
```

Material decisions must never become `user-approved` from inference alone.

**Tests:** hallucinated/inferred decision remains inferred; credential-like text is excluded; deterministic repository fact retains source.

## Phase 6: Runtime API Read Surface

Implement secure local runtime service and read-only endpoints first:

- health/status;
- project identity;
- workflow state;
- memory/list/query;
- decisions;
- skills/agents metadata;
- providers/status;
- settings/effective values.

Security baseline:

- loopback binding;
- runtime session token/capability;
- strict origin/CORS policy;
- no secrets in diagnostics.

**Gate:** read-only Control Center prototype can operate without importing runtime internals.

## Phase 7: Control Center Foundation

Build the local web UI with:

- Overview;
- Workflow;
- Memory;
- Decisions;
- Providers;
- Settings.

Use a lightweight build/runtime strategy compatible with DK packaging goals. Avoid introducing a desktop shell.

Implement manual open command.

**Gate:** developer can inspect active project, lifecycle, memory provenance/status, provider health, and settings.

## Phase 8: Automatically Open Control Center

Implement the approved setting:

```text
Automatically open Control Center
[ On / Off ]
Default: Off
```

Requirements:

- global/user setting;
- optional project override;
- project > global > default precedence;
- interactive-context detection;
- suppress CI/headless/test launch;
- validate local endpoint before open;
- duplicate-launch suppression;
- auto-open failure does not block DK startup;
- manual open always remains available.

**Gate:** behavioural tests cover On, Off, inherited, project override, CI/headless, stale endpoint, and repeated activation.

## Phase 9: Governed Write Surface

Add Runtime API/UI operations for:

- edit;
- archive;
- supersede;
- forget;
- candidate approve/reject;
- settings update;
- provider activate/deactivate where permitted.

All writes reuse authoritative storage locks/transactions and policy validation.

Authority promotion gets a dedicated confirmation event and cannot happen through a generic edit request.

**Security gate:** CSRF/cross-origin tests pass before browser writes are considered complete.

## Phase 10: Knowledge and Code Intelligence Abstractions

Implement provider-neutral capability interfaces for:

- knowledge list/query/read;
- code status/files/search/explore/node/callers/callees/impact.

Baseline can use native repository capabilities where advanced graph functionality is absent.

Control Center gains Knowledge and Code Intelligence views as capabilities become available.

## Phase 11: TencentDB Agent Memory Adapter

Build optional adapter against the DK provider contract.

Target capability mapping:

- Chat Memory -> memory source;
- Skills -> provider skill assets;
- Wiki -> knowledge;
- CodeGraph -> code intelligence.

Constraints:

- no mandatory Tencent proxy;
- no mandatory Docker for DK baseline;
- no mandatory Tencent dependency in `package.json` unless adapter packaging is deliberately optional/separate;
- provider content remains untrusted;
- provider health/failure is explicit;
- credentials are not stored in DK memory.

**Gate:** uninstalling/disabling Tencent does not break core DK memory or Control Center.

## Phase 12: Agent Loadouts and Skill Governance

Expose effective agent loadouts in Control Center:

- applicable memory scopes;
- skills;
- knowledge bindings;
- code-intelligence capability;
- exclusions.

Add governance for project-learned/provider skill candidates before they can be treated like trusted DK procedures.

## Phase 13: Import, Export, Migration and Recovery

Implement:

- portable DK memory export;
- safe import with trust classification;
- schema migration/versioning;
- index/cache rebuild;
- corrupt-record diagnostics;
- provider migration boundaries where practical.

Imported records default to non-authoritative classification until provenance/authority can be established.

## Phase 14: Cross-Platform Integration

Validate Development Kit activation and Control Center behaviour across supported environments:

- Antigravity;
- OpenCode;
- Claude Code;
- Cursor;
- VS Code with GitHub Copilot;
- Cline;
- Windsurf;
- standalone installation.

No platform-specific adapter may become required for core memory persistence.

## Phase 15: Full Security and Quality Validation

Required test/evaluation families:

### Memory correctness

- approved decision recall;
- supersession;
- stale facts;
- provenance;
- authority separation;
- project isolation;
- context-budget behaviour.

### Safety

- remembered approval cannot bypass gates;
- imported prompt injection remains untrusted;
- secrets not persisted;
- cross-origin localhost writes rejected;
- provider failure cannot claim success;
- provider output cannot authorize tools.

### Control Center

- manual launch;
- auto-open On/Off;
- default Off;
- project/global precedence;
- no CI/headless launch;
- duplicate suppression;
- loopback binding;
- stale runtime recovery;
- accessibility and keyboard navigation.

### Regression

- existing commands;
- Autopilot state recovery;
- Next-Step Guidance;
- installer modes;
- platform adapters;
- external research contract;
- canonical plugin mirror;
- docs validation;
- release validation.

## Phase 16: Documentation and Release Readiness

Before release:

- convert planned docs to implemented/current wording only where verified;
- document Control Center launch and settings;
- document memory inspection/correction;
- document provider configuration;
- document security/trust semantics;
- update README capability tables;
- update command/reference docs for any new command;
- update changelog;
- add release/migration notes;
- run full `npm run release:validate` plus v0.7-specific test gates.

## Proposed v0.7 Release Gate

v0.7 is not release-ready unless all are true:

- local memory works without external services;
- project isolation is verified;
- approval bypass tests pass;
- stale/superseded memory behaves correctly;
- Control Center binds to loopback by default;
- browser writes are protected;
- auto-open defaults Off and respects interactive/headless rules;
- Control Center failure does not break normal DK operation;
- provider failure degrades gracefully;
- Tencent adapter, if shipped in v0.7, remains optional;
- all pre-v0.7 release validation still passes.
